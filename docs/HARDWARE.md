# Motorola MH7021 / MH7022 — hardware reference

Everything here was established on real units and verified across reboots. All of it is
**model-level**; nothing in this file is specific to an individual unit.

## SoC and board

| | |
|---|---|
| SoC | Qualcomm IPQ4019, quad-core ARMv7 |
| RAM | 256 MiB |
| Flash | 32 MiB SPI-NOR (Winbond W25Q256) |
| U-Boot | 2012.07, QCA "TWB Bootcode", prompt `(IPQ40xx) #` |
| `machid` | `0x8010006` |
| Vendor device tree | `AP-DK07.1-C1` |
| Console | 115200 8N1, **3.3 V** (the UART clock caps the rate) |

## Radios

| device | chip | band | OTP board id | range |
|---|---|---|---|---|
| `wifi0` | IPQ4019 | 2.4 GHz | 20 | — |
| `wifi1` | IPQ4019 | 5 GHz-low | 29 | **5100–5400 MHz** |
| PCIe | **QCA9888** | 5 GHz-high | 23 | **5450–5900 MHz** |

The QCA9888 is the reason a dedicated mesh backhaul works: it is a separate radio from the
two client-facing ones.

**Consequence worth knowing:** because the QCA9888 starts at 5450 MHz, *every* channel it can
use below UNII-3 is a DFS channel. There is no non-DFS channel lower than 149 available to
the backhaul, and 802.11s on DFS fails on this driver/firmware (`DFS start_dfs_cac() failed`,
mesh interface stays DISABLED). Channels 36–64 show as `disabled` on that phy.

Pre-calibration data sits at ART+0x1000 / +0x5000 / +0x9000, `0x2f20` bytes each, exposed
via nvmem so the driver logs `cal pre-cal-nvmem` for all three radios.

## MAC addresses

**Factory MACs live in ART**, not in U-Boot's environment:

| offset | equals |
|---|---|
| `ART+0x0` | U-Boot `wanaddr` |
| `ART+0x6` | U-Boot `ethaddr` (label MAC) |

The DTS exposes these as `mac-base` nvmem cells `macaddr_art_0` / `macaddr_art_6`, and
`&gmac` takes `macaddr_art_6`.

**Without that nvmem wiring the EDMA driver logs `using random MAC address` on every boot** —
which presents as "the MAC addresses change every reboot". If you see that, the nvmem cells
aren't being read.

Note: on OpenWrt 25.12 the `wan` interface takes `ART+0x0`, so a unit upgraded from an older
build may see its WAN MAC change — and with it, its DHCP lease from upstream.

## Ethernet

ESS switch with two external jacks:

| jack | PHY | switch port | OpenWrt name |
|---|---|---|---|
| 1 | PHY3 | swport4 | `lan` |
| 2 | PHY4 | swport5 | `wan` |

Both report `PHY [90000.mdio-1:03] driver [Qualcomm QCA8072]` when correctly initialised.

### Two U-Boot gotchas that cost real time

**1. This U-Boot has no `boot` command.** Use `run bootcmd` or the vendor's `bootipq`.

**2. `bootipq` is unsafe after a reboot from OpenWrt.** It hits a "Crashdump magic" detour
that leaves the switch PHYs dead, so `lan`/`wan` never appear. Replace `bootcmd` on every
unit — `tools/flash_uboot.py` does this.

**3. Autoboot needs U-Boot's Ethernet init before the kernel starts**, or the PHYs are never
found and the kernel logs `failed to connect to PHY: -EINVAL`. A `ping` in `bootcmd`
triggers the init (`Net: … ipq40xx_ess_sw_init done`) at a cost of ~1.6 s. `mii info` does
**not** work for this. A proper kernel-side fix is the main outstanding upstreaming item.

## GPIOs

| function | GPIO | notes |
|---|---|---|
| reset button | 18 | active-low |
| WPS button | 49 | active-low |
| status LED — green | 24 | active-high |
| status LED — red | 27 | active-high |
| status LED — blue | 28 | active-high |
| PCIe PERST | 38 | |
| MDIO / PHY reset | 41 | |

The three LED GPIOs form one RGB indicator; `neon-led` drives it from actual system state.

## Flash layout (MTD)

| partition | offset | size |
|---|---|---|
| SBL1 | `0x0` | |
| MIBIB | `0x40000` | |
| QSEE | `0x60000` | |
| CDT | `0xc0000` | |
| DDRPARAMS | `0xd0000` | |
| APPSBLENV | `0xe0000` | `0x10000` |
| APPSBL | `0xf0000` | |
| **ART** | **`0x170000`** | **never erase** |
| firmware | `0x180000` | `0x1a70000` |
| cli_factory_ext | `0x1d00000` | |
| storage | `0x1f00000` | |

**ART holds per-unit radio calibration and the factory MACs. It cannot be regenerated.**
Dump the whole chip before flashing anything, and keep that dump.

`APPSBLENV` is a single copy with no redundant-flag byte, so the `uboot-envtools` entry is:

```
motorola,mh7021) ubootenv_add_uci_config "$(find_mtd_part APPSBLENV)" "0x0" "0x10000" "0x10000" ;;
```

That config is generated by a `uci-defaults` script, which **only runs on a clean first
boot**. After a config-preserving `sysupgrade` you may find `/etc/fw_env.config` missing and
`fw_printenv` unusable — regenerate it or do one factory-reset boot.

## Board files

`board-2.bin` for each radio comes from the vendor rootfs at
`/lib/firmware/ath10k/QCA4019/hw1.0/board-2.bin` and
`/lib/firmware/ath10k/QCA9888/hw2.0/board-2.bin`. On these units they are **24468 bytes**
(QCA4019) and **12244 bytes** (QCA9888) — if a build stages different sizes, the vendor data
did not make it in and the radios will come up on generic calibration or not at all.

Package them with `ath10k-bdencoder`, naming each entry for the `bmi_id` the kernel reports:

```
ath10k-bdencoder -c ipq-wifi/board-motorola_mh7021.qca4019.json -o board-motorola_mh7021.qca4019
```

If a radio logs `failed to fetch board data` or no `board_file` line at all, its `bmi_id`
isn't in the JSON.

## Flash-space constraint

The overlay is ~17.7 MiB. That is tight enough to matter: staging a ~10 MiB rollback image
on the overlay can starve the **first boot** after an upgrade, which then fails to write
`/etc/board.json` and `/etc/fw_env.config`. A missing `board.json` breaks
`/lib/wifi/mac80211.uc` with `Type error: Passed value is neither a string nor an object`,
and the unit comes up with **no wireless interfaces at all** — looking bricked while being
perfectly healthy. Leave real headroom, or don't stage large files on the overlay.
